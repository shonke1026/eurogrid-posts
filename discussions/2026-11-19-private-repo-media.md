## Claude回答

### 2026-11-19 01:19（即時の受け口）

**Q1. 非公開のあとも定期タスクは本体を読み書きできるか**
- 結論：たぶんできる。ただし未確認。定期タスクの clone・push は、この環境の git の中継（Claude の GitHub App とつないだ権限）を通っている。今日の clone も認証なしの URL で通ったが、いまは公開なので、非公開でも通る証拠にはならない。
- 確かめ方：非公開にした直後に、協議の受け口を1回だけ手で動かし、clone と discussions/ への push が通るかを見る。11/12 の test-push と同じ形で、試し用のファイル1つでやればよい。毎朝の案のタスクも、次の朝に clone の段で止まっていないかを見る。
- だめだったときの代わり：GitHub の Claude アプリを本体のリポジトリに入れ直す（アプリの対象リポジトリの設定）。それでも通らなければ、GitHub の MCP ツール（ファイルの読み・書き）で書く形に切り替える。どちらも試していない。
- 別の大事な点：GitHub Actions の publish.yml は15分ごとに動いている。公開リポジトリは Actions が無料で使い放題だが、非公開だと無料枠（Free プランで月2,000分の見込み、未確認）がある。1回1分と数えても 96回×30日で約2,900分になり、枠を超えるかもしれない。非公開にする前に、cron の間隔を広げる（たとえば30〜45分ごと、または予約の時刻の前後だけ）か、使用量の画面で1回あたりの分数を見ておきたい。

**Q2. チャッピーは非公開の discussions/ を読めなくなるか**
- 結論：読めなくなる見込みが高い。チャッピーは公開ページとして GitHub を読んでいるはずで、非公開のページは 404 になる。ただ、チャッピー側に GitHub の連携が入っていれば読めるかもしれない。未確認。
- 確かめ方：非公開にしたあと、チャッピーに今ある相談ファイルの URL を1つ渡して、「素材」の1行目を答えてもらう。合っていれば読めている。
- 読めなかったときの案：相談ファイルを置いたら、同じ中身をメールでチャッピーに送る形がいちばん手間が少ない。件名は今の「三者協議 相談｜ファイル名」とは別の名前にしないと、この受け口がまた動く。メールを送るのはメインの会話か運営者の手で、無人のタスクからは送らない（いまの決まりでは運営者の2つのアドレス以外に送れない）。中身は素材と質問票だけでよい。

**Q3. eurogrid-media で投稿前の画像が見える問題**
- 結論：小さい。気にするなら直前に置く形で避けられるが、いまは受け入れて進めてよいと思う。
- 理由：第三者が見るには、リポジトリの存在を知って、中身を見に来る必要がある。フォロワー数を考えると、わざわざ見に来る人はほぼいない。ネタバレ配慮の投稿でも、画像を置くのはレース後なので、結果が先に出る心配はレース前の画像にはない。困るのは、OK前の案の画像を置いてしまうこと。これは「OKのあとだけ置く」で防げるし、今の決まり（OK前は push しない）のままでよい。
- 避け方：ファイル名を推測しにくくしても、リポジトリの一覧から見えるので効果は薄い。効くのは「投稿の直前に置く」。ただしそれには Actions から eurogrid-media に push する鍵（トークン）が要り、Secrets の登録も要る。今の手間に見合わないので、まずは「OK後に置く」で始め、困ったら考える、でいいと思う。

**Q4. 切り替え後、最初に確かめる投稿**
- 結論：テスト用の投稿を先に1回。実際の投稿で試すのは、失敗したときに予約の時刻を外すので避けたい。
- やり方：publish.py には --check（フォルダを指定して確かめる）があるので、まず --check で eurogrid-media の URL が全部開けるかだけを見る。Instagram・Threads へ実際に出すテストは、運営者が要ると言えば。出すなら、すぐ消せる Threads のテキスト＋画像1枚が軽い。
- 止め方：URL が1つでも開けなければ、その投稿全体を止めて理由を出す形でよい。画像を抜いて文だけ出すと、カルーセルの順番や意味が崩れる。理由は「どのファイルの URL が、何番（404 など）で開けなかったか」まで出す。
- 注意：publish.py の REPO は環境変数 GITHUB_REPOSITORY を使っている。Actions の中ではこれが本体の名前になるので、画像の置き場所は別の変数（たとえば MEDIA_REPO）にしないと、本体を向いたままになる。

**Q5. 過去の posts/ の分も移すか**
- 結論：移さなくていい。これからの分だけ。
- 理由：Instagram・Threads は、投稿の時に画像を取り込んで自分のところに保存する。出たあとに元の URL が消えても、出た投稿は消えない（ふつうの動きとしてはそう。Eurogrid で確かめてはいない）。だから過去の分を移しても得るものはない。
- 例外：まだ出ていない予約の投稿（posts/ にあって published.json が無いもの）は移す。そうしないと非公開にしたとたん失敗する。非公開にする前に、未投稿のフォルダを数えておく。
- あとで消す運用：今は要らない。大きいのは動画で、リポジトリの容量が1GBに近づいたら考える。消すなら「出てから30日たった動画」のような決まりを1つだけ。

**Q6. 誰がどう実行するのが楽か**
- 結論：リポジトリ作成も非公開化も、運営者が GitHub の画面で1回ずつやるのがいちばん速い。合わせて2〜3回の操作。
  1. 新しいリポジトリを作る：右上の「＋」→「New repository」→ 名前 eurogrid-media、Public、「Add a README」にチェック → 作成（1回）
  2. Claude のアプリを eurogrid-media にも入れる：GitHub の設定 → Applications → Claude → リポジトリの対象に eurogrid-media を足す（1回。全部のリポジトリが対象なら不要）
  3. 本体を非公開に：eurogrid-posts の Settings → 一番下の Danger Zone → Change visibility → Private（1回。確認コードが要るかもしれない）
- 順番：1と2のあと、Claude が画像の置き直しと publish.py の変更を入れ、--check が通ってから3。逆にすると、その間の投稿が止まる。
- API で作れなかった理由：この環境の GitHub の権限は、本体の1つのリポジトリに絞られている。新しいリポジトリの作成は、その範囲の外になる。正確なエラーは見ていないので、これは推測。

**Q7. 公開中に見られた分の手当て**
- 結論：非公開にするだけでいい。そのうえで残るリスクを知っておく、で十分。
- 残るリスク：
  - 公開中に誰かが clone・フォークしていれば、その写しは残る。非公開にしても消せない。フォークの数は Insights で見られる。
  - メールのアドレスは、迷惑メールが少し増えるくらいの話。気になるなら、Gmail の迷惑メールのフィルタで足りる。
  - 鍵（トークン）が履歴に入っていたら、これだけは別。もし入っていれば、無効にして作り直す必要がある。決まりで書いていないはずだが、GitHub の secret scanning（鍵の自動検出）を1回かけて確かめると安心。
  - Instagram の内部ID（publish.py の初期値）は、公開されても単体では悪用しにくい。
- 書き換え・伏せ字をしないという決定には賛成。やっても、上のとおり写しは消せない。
