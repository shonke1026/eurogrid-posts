**Q1. auditor にも足すべき。ただし機械で見られるものだけ。**
- auditor 側に持たせる：誤字脱字、句読点の位置、同じ文の使い回し（過去の記事との一字一句の一致）、定型句（CLAUDE.md の4にある「お届けします」など）の検出。auditor.md のチェックリスト10に「文章」として1行足すのがいちばん軽い。同じ文の一致は scripts/check_post.py に note-body 用の検査として足せそう（過去記事の本文と、たとえば20字以上の一致を出す）。ただし作るのはメインの会話で、まだ試していない。
- ユーロ側に残す：「AIっぽさ」の判定、体言止めの多さ、締め方の重なり。目で読んで決めるもので、基準を数字にしにくい。
- 理由：auditor は「通す・戻す」を判断する担当なので、判定がぶれるものを持たせると戻す理由がぶれる。両方で同じ観点を見ると二重になるので、分ける線は「機械で引っかけられるか」にするのがわかりやすい。

**Q2. ユーロ案に賛成。**
- 固定してよい：見出しの並び、冒頭のPR表記、末尾の案内（SNSのリンク、アソシエイトの表示）。これはそもそも決まった文。
- 回ごとに変える：本文の地の文、締めの文、アドバイス（今回の「観光は前後に寄せるのが現実的です」はこちら）。CLAUDE.md の4「形を毎回そろえない」とも合う。
- 迷ったら「シリーズを続けて読んだ人が、同じ文に気づいて手抜きと感じるか」で決めればいいと思う。

**Q3. 問題になりそうな点は4つ。**
1. ルールが無い：agoda のリンクは、CLAUDE.md にも platforms/note.md にも書かれていない（8はAmazonの決まりだけ）。冒頭のPR表記の文が「アフィリエイトリンク（PR）」でAmazon以外にも当てはまる形なので、agoda にも使うか、末尾にアソシエイトのような表示が要るかを、運営者が決めてルールに足したほうがいい。いまの auditor は agoda を見る項目を持っていない。
2. 画像へのリンク：note で画像にリンクを付けられるかは、こちらでは未確認。付けられなかったときのために、直下のテキストリンク1行を必ず残すのは良い形だと思う。
3. リンク切れの点検：画像のリンクは本文の文字として見えないので、目で見ても漏れる。公開後の記事を開いて、バナーとテキストの2つのリンク先が同じで、開けるかを確かめる手順を1つ足すのがいい。check_post.py の note-body が agoda のリンクを拾えるかは未確認（いまは Amazon のリンクだけ見ている）。
4. note 以外：X・Threads・Instagram に Amazon を貼らない決まり（8）と同じ考えで、agoda も note の中だけにしておくのがいいと思う。広げるかどうかはお金の方針なので、運営者が決めること。

**Q4. 同じ方式でいい。**

Q1. auditorへの文章チェック追加

追加に賛成。ただし、Claudeとユーロの役割を完全には分離しない。

Claude auditorの必須項目：

誤字脱字

句読点の異常候補

NG表現の一致

他記事との文章重複

略語の初出説明漏れ

文末の断片候補

ユーロの責任項目：

読者にとって自然か

日本語として意味が通るか

AI特有の硬さや不自然さがないか

MotoGPの記事にビジネス用語が混入していないか

機械的なチェックは見落とし削減のために使い、人間的な文章判断を置き換えない。

Q2. シリーズ記事の同一文

ユーロ案に賛成。

固定を許容するのは、共通見出し、PR表記、著作権表示、運営アカウントの説明など。

本文の導入、観光上の助言、記事の結論は原則として記事ごとに書く。

ただし、同じ事実を同じ用語で説明することまで禁止しない。文章の一致だけで不合格にするのではなく、重複の目的で判定する。

Q3. agodaリンクの標準化

バナー画像と、その直下のテキストリンクを併用する方式に賛成。

必要な確認項目：

バナー画像をクリックできること

テキストリンクが機能すること

両方が意図した予約先を指すこと

PR表記が明確であること

スマートフォンでも認識できること

バナー画像にリンクを設定できるかは、noteの編集画面で実測確認が必要。現時点では機能を保証しない。

テキストリンクは必須として残す。 画像が読み込めない環境でも予約導線を維持でき、リンク先の確認もしやすい。

note以外へのアフィリエイトリンク展開は、現行の媒体別運用ルールを優先し、別の運営判断なしに拡大しない。

Q4. 同じ指摘2回で仕組みを修正する方式

賛成。ただし、修正条件を次のようにする。

初回：個別修正、ミス記録、原因分類

2回目：テンプレート・検査ルール・制作工程のいずれかを改善

重大な初回ミス：回数を待たずに対策

改善後は、該当パターンを含むテスト原稿で再検出できることを確認する。

単にチェックリストへ項目を追加するだけでは、改善完了としない。

Q5. 投稿案メールに全文を掲載すべきか

賛成。ただし、メールを唯一の正本にしない。

現状の問題は、ユーロが原稿の一部分しか見られず、発信前に全文の品質を確認できないこと。

推奨構成は以下。

正本：リポジトリまたは共有可能な原稿ファイル

通知メール：相談ID、版・更新情報、全文への参照、必要に応じて本文全文

auditor：全文を取得してチェック

ユーロ：チェック結果と原稿の同一性を確認

全文の取得経路が確実でない現行環境では、メールに全文を含めることを暫定対策として支持する。

ただし、GitHubに保存する際の非公開情報の扱いは、リポジトリの公開設定に従って管理する。
